## Question 1 (50 marks): RetailMax big data platform

Key facts: 2,000 stores, 30 countries; per day 15M POS sales (about 175 per second), 5M loyalty events, 500K social posts, 50 TB CCTV video; reports take 3 weeks; video deleted after 7 days; no real-time stock; bad data costs $50M a year.

Sizing: 50 TB video x 3 replicas = 150 TB raw disk per day, so cold video needs erasure coding (about 1.5x) or cheap object storage.

### (a) Hadoop ecosystem architecture, at least six components (15 marks)

```
POS, loyalty, social -> Kafka/Flume -> HDFS lake (raw/clean/curated) -> Spark (stream, batch, MLlib)
ERP, supplier DBs    -> Sqoop       ->                               -> Hive -> BI dashboards
                                                                      -> HBase (live stock)
            YARN (resources) | ZooKeeper (coordination) | Oozie (scheduling)
```

| Component | Role at RetailMax |
|---|---|
| Kafka | Streams sales, loyalty and stock events; buffers peaks; enables real-time stock |
| Flume | Collects social feeds, logs and CCTV metadata into HDFS |
| Sqoop | Bulk import from ERP and supplier databases |
| HDFS | Data lake on cheap disks; keeps video beyond 7 days; replication for safety |
| YARN | Shares cluster CPU and memory between Spark, Hive and MapReduce |
| Spark | Streaming stock updates, cleaning, joins, demand forecasts, sentiment |
| Hive | SQL warehouse on partitioned ORC tables; cuts 3-week reports to hours |
| HBase | Millisecond reads and writes for live stock and customer profiles |
| Oozie / ZooKeeper | Schedule nightly pipelines; keep master services highly available |

- Flow: ingest, store raw, stream to HBase, nightly clean and aggregate, Hive for BI, decisions.

Remember: six components, role plus reason, data flow, case problems.

### (b) Data governance framework (15 marks)

- **Roles:** governance council (approves policy), data owners (business heads), stewards (define and fix data), custodians (IT run storage and security).

| Area | Rule | Tool |
|---|---|---|
| Data quality | Valid ids, price > 0, no duplicates, quarantine bad rows | Spark checks, quality dashboard |
| Metadata | Every dataset registered with owner, source, sensitivity | Hive Metastore, Apache Atlas |
| Master data | One id for customer, product, store across systems | MDM golden records |
| Security | Encryption at rest and in transit, strong login | Kerberos, Ranger, Knox |

| Lifecycle | Hot, warm, cold tiers; retention and legal hold | HDFS storage policies, purge jobs |

- **Why:** quality attacks the $50M loss; lineage builds trust; privacy and compliance avoid fines (up to 4% of turnover under GDPR); lifecycle controls video cost.
- **Value:** trusted data for ML, faster decisions, lower risk.

Remember: roles, eight areas, tools, $50M justification.

## Question 2 (25 marks): GlobalPay and the CAP theorem

Key facts: 100M transactions/day, peaks 10K/s, 99.999% uptime (about 5 minutes down a year); Singapore to London partition; $15M compensation, $5M lost revenue, 25% trust drop, 3 regulators.

### (a) Investigate with CAP and recommend (10 marks)

- **C:** every read sees the latest write. **A:** every request gets an answer. **P:** works despite network splits.
- **Partition happened:** the Singapore to London link failed; in a global system P is not optional.
- **Balances appeared then vanished:** one side kept accepting writes (chose A), then conflicts were rolled back.
- **Timeouts:** other services waited for the remote side (chose C).
- **Why not all three:** with the link down, London cannot see a Singapore write; it must return an old value (lose C) or refuse (lose A).
- **Recommend CP for the ledger:** consensus database (Raft/Paxos, e.g. Spanner, CockroachDB), 5 replicas in 3 regions, majority commit, home region per account, idempotency keys.
- **AP is fine** for catalogues, notifications and dashboards.
- **PACELC:** ledger is PC/EC, accepting about 150 to 200 ms extra latency for correctness.

Remember: define C, A, P; map symptoms; CP with quorum; PACELC.

### (b) Consistency or availability? (8 marks)

- **Decision:** consistency for anything that touches a balance.
- **Cost evidence:** inconsistency cost $15M plus trust and regulators; unavailability cost $5M.
- **Customers and merchants:** a delayed payment beats a confirmed one later reversed.
- **Banks and regulators:** accurate settlement is a legal duty.
- **Fraud:** stale balances allow double spending.
- **Soften the impact:** read-only last balance with timestamp, queue payments as "pending", clear error messages, majority quorum so only the minority side stops.

Remember: choose C, stakeholders, case numbers, degraded modes.

### (c) Consistency models (7 marks)

| Model | Guarantee | Fits |
|---|---|---|
| Strong | Reads always see the latest write | Balances, transfers, bookings |
| Eventual | Replicas converge later; reads may be stale | Likes, catalogues, feeds |
| Causal | Cause seen before effect by everyone | Comments, chat, activity history |

- **GlobalPay:** strong for the ledger; read-your-writes or causal for a user's history; eventual for analytics and notifications.
- **Impact:** strong adds latency, so use home regions; eventual is fast but unsafe for money.

Remember: three models with examples, strong for money.

## Question 3 (25 marks): HealthInsight MapReduce

Key facts: 500 hospitals, 50 TB/day, one SQL server takes 12 hours. 50 TB in 128 MB blocks is about 400,000 map tasks running in parallel.

### (a) MapReduce for regional disease statistics and high-risk patients (15 marks)

```
HDFS blocks -> Mapper -> Combiner -> Partitioner -> Shuffle/Sort -> Reducer -> HDFS -> Hive
```

- **Mapper:** parse each admission, drop invalid rows, de-identify, look up region from a cached hospital table; emit key (region, diagnosis, month), value (1, stay_days, died).
- **Combiner:** sums counts on the map node; 1M records with 2,000 keys send 2,000 records. Safe because sum is associative.
- **Partitioner:** hash(region, diagnosis) mod R so each key meets in one reducer and big regions spread out.
- **Shuffle and sort:** groups all values of a key together for the reducer.
- **Reducer:** total cases, average stay (from sum and count), mortality rate per region and disease.
- **High-risk job:** key = patient_id; tag admissions, labs and wearable data; reducer joins them and flags 3+ admissions a year, readmission within 30 days, abnormal labs.

| Phase | Benefit |
|---|---|
| Mapper | Thousands of tasks run where the data is |
| Combiner | Cuts network traffic |
| Partitioner | Balances load, avoids hot reducers |
| Reducer | Small aggregated output for reports |

Remember: keys and values, combiner safety, de-identify, risk rules.

### (b) Shuffle and sort, and optimisation (10 marks)

- **Steps:** map buffer (100 MB) fills, partition and sort, spill to disk, merge, reducers fetch over HTTP, merge sort, group by key.
- **Expensive because:** disk write and read twice, all-to-all network, n log n sorting, serialization, reducers wait for all maps, skew.
- **Optimise:**
  - combiner for sums and counts;
  - compress map output (Snappy or LZ4);
  - drop unused columns and bad rows in the mapper;
  - map-side join for small hospital and ICD tables;
  - tune sort buffer and reducer count;
  - salt or custom partitioner for hot keys;
  - process only new daily partitions; ORC input.

Remember: buffer, spill, fetch, merge, group; five optimisations.

## Question 4 (25 marks): MediaStream HDFS

Key facts: 200M subscribers; 1.65 PB new data per day (about 5 PB raw at 3x); NameNode memory at 95%; millions of small files; replication costs $3M a month.

### (a) NameNode, DataNode and Secondary NameNode (10 marks)

```
Client --metadata--> NameNode (namespace + block map in RAM) <--checkpoint--> Secondary NN
   \                     ^ heartbeats (3 s), block reports
    \--data directly--> DataNode  DataNode  DataNode ...
```

- **NameNode:** holds namespace, block locations and permissions in RAM; logs changes (fsimage + edits); detects dead nodes; picks rack-aware locations.
- **DataNode:** stores blocks on local disk; heartbeat every 3 s; serves reads; write pipeline DN1 to DN2 to DN3; checksums.
- **Secondary NameNode:** merges fsimage and edit log for fast restart. **Not a failover node.**
- **Production:** NameNode HA (active and standby via JournalNodes and ZooKeeper) and Federation to split `/video`, `/logs`, `/metadata`.
- **Design reason:** data never passes through the master, so throughput grows with DataNodes.

Remember: roles, Secondary is checkpointing, HA, Federation.

### (b) Impact of millions of small files (15 marks)

- **Rule:** each file, directory and block costs about 150 bytes of NameNode RAM.
- **Example:** 100 TB as 1 MB files = 100M files = 200M objects = about 30 GB heap; as 128 MB files only about 245 MB.

Problems:
- NameNode heap full even with free disk.
- Long garbage collection pauses and client timeouts.
- Slow restarts (huge fsimage).
- Millions of RPC calls slow every user.
- One task per file, so start-up time exceeds work time.
- Many disk seeks instead of sequential reads.

Fixes:
- Daily compaction into 256 MB files (Spark `coalesce`, Hive merge).
- Store as ORC, Parquet, SequenceFile or Avro; HAR for old files.
- Per-record metadata in HBase.
- HDFS Federation or Apache Ozone.
- Erasure coding (RS 6+3, about 1.5x) for cold data to cut the $3M replication bill; compact first.

Remember: 150 bytes rule, calculation, effects, fixes.

## Question 5 (25 marks): RetailDirect and Hive

Key facts: 50M customers, 500K products, Java MapReduce today; needs SQL for non-programmers, reports under 2 hours, 5 years of history, 20% monthly user growth.

### (a) Hive, Pig and Spark SQL (15 marks)

| Aspect | Hive | Pig | Spark SQL |
|---|---|---|---|
| Language | SQL | Dataflow script | SQL and DataFrames |
| Users | Analysts, BI | Data engineers | Engineers, data scientists |
| Engine | Tez, MapReduce, Spark | MapReduce, Tez | Spark, in memory |
| Speed | Good batch; LLAP for interactive | Batch only | Fast, multi-step |
| Best for | Shared warehouse, BI reports | Complex ETL, nested data | Heavy joins, ML, streaming |

- **Hive:** warehouse of partitioned ORC tables; daily reports through HiveServer2 meet the SQL need.
- **Spark SQL:** sales x customers x products joins, segmentation, MLlib, same metastore.
- **Pig:** only existing ETL on raw logs; new ETL in Spark.
- **Speed up the slow join:** partition sales by date; bucket sales and customers on customer_id; broadcast the 100 MB products table; ORC with statistics; pre-aggregated daily tables.
- **Growth:** scale out on YARN or cloud; LLAP or Trino for many users.

Remember: comparison, when to use each, join tuning.

### (b) Hive architecture (10 marks)

```
BI tools (JDBC/ODBC) -> HiveServer2 -> Driver -> Compiler <-> Metastore
                                  -> Tez/MapReduce/Spark on YARN -> HDFS
```

| Component | Role |
|---|---|
| HiveServer2 | Accepts queries from many users, sessions, authentication |
| Driver | Controls query life cycle: compile, execute, fetch |
| Compiler | Parses SQL, checks schema, builds and optimises the plan |
| Metastore | Tables, columns, partitions, locations, statistics in MySQL or PostgreSQL |
| Execution engine | Runs the task DAG on YARN over HDFS |

- **Query path:** BI tool, HiveServer2, Driver, Compiler asks Metastore, optimiser prunes partitions and picks map join, DAG runs on YARN, results return.

Remember: four components, query steps, diagram.
