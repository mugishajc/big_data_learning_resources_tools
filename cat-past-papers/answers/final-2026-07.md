## Question 1 (40 marks): Real-time sentiment pipeline with Kafka and Spark

Key facts: 500 million posts a day (about 5,800 per second, over 20,000 per second at peak), 5 platforms, results in under 5 seconds, exactly-once.

### (a) Kafka architecture and topic design (10 marks)

- **Broker**: a Kafka server that stores partitions. Start with 5 to 6 brokers.
- **Topic**: a named stream of records. **Partition**: an ordered log; the unit of parallelism.
- **Producer** writes records (partition chosen by hashing the key); **consumer** reads and tracks its offset.
- **Replication**: factor 3 with `min.insync.replicas=2`, so one broker can fail with no data loss.
- **One raw topic per platform**: each API has its own format and rate, and an outage on one does not slow the others.
- **Shared cleaned topic** with one Avro schema, checked by a schema registry.
- **Partitions**: 20,000 posts/s at about 1,000 per consumer needs at least 20; plan 24 to 48 for busy topics.
- **Keys and retention**: key raw posts by `post_id`, scores by brand; keep raw data 7 days for replay.

```
social.twitter.raw  social.facebook.raw  ... (one per platform)
        |  Spark cleaning
social.all.cleaned  (Avro schema)
        |  Spark sentiment
sentiment.scores ---> dashboards, APIs
        |  Spark trends
alerts.trending  ---> alert service
```

Remember: partitions, replication 3, topic per platform, schema registry.

### (b) Consumer groups and parallelism (10 marks)

- **Consumer group**: consumers that share a topic; each partition goes to exactly one consumer in the group.
- **Max parallelism = partition count**: 24 partitions allow 24 consumers; a 25th sits idle.
- **Sizing**: 24 consumers handle about 830 posts/s each at peak, keeping latency well under 5 seconds.
- **Several groups** (sentiment, trends, archive) read the same topic independently, each with its own offsets.
- **Rebalancing**: when a consumer joins, leaves or crashes, its partitions move to the others.
- **No skipped data**: the new owner resumes from the last committed offset.
- **Cooperative sticky assignor**: only the moved partitions pause, so the group keeps working.
- **Consumer lag** (latest offset minus committed offset) rising is the signal to add consumers.

Remember: one partition per consumer, lag, rebalancing, cooperative sticky.

### (c) Processing guarantees (10 marks)

| Guarantee | Offset committed | On failure | Effect |
|---|---|---|---|
| At-most-once | before processing | message lost | sentiment under-counts |
| At-least-once | after processing | message repeated | duplicates, false alerts |
| Exactly-once | with the output, atomically | no loss, no duplicates | correct counts |

- **Idempotent producer** (`enable.idempotence=true`) drops duplicate retries.
- **Transactions** write output records and consumer offsets together, or not at all.
- **`read_committed`** consumers never see aborted records.
- **Spark**: checkpointing, a replayable source (Kafka) and an idempotent sink give end-to-end exactly-once.
- **Choose exactly-once**: clients trade and react to alerts, so duplicates or losses cost money and trust.
- **Cost**: a few tens of milliseconds of latency, which still fits the 5 second target.

Remember: idempotence, transactions, read_committed, checkpoint.

### (d) Event time vs processing time (10 marks)

- **Event time**: when the post was written. **Processing time**: when Spark handles it.
- **Late data**: API rate limits, network problems and retries delay posts by seconds or minutes.
- **Correct windows**: event time counts a post in the minute it was written.
- **No fake spikes**: a throttled backlog arriving at once is spread back over the right minutes.
- **Reproducible**: replaying from Kafka gives the same results.
- **Watermark**: how long to wait for late posts; longer is more accurate but slower and uses more memory.

```python
trend = (parsed
    .withWatermark("event_time", "2 minutes")
    .groupBy(F.window("event_time", "1 minute", "30 seconds"), "topic")
    .agg(F.count("*").alias("mentions"), F.avg("sentiment").alias("avg_sentiment")))
query = (trend.writeStream.outputMode("update")
    .option("checkpointLocation", "/chk/trends")
    .trigger(processingTime="2 seconds").format("console").start())
```

Remember: event time, watermark, window, late data.

## Question 2 (20 marks): Polyglot persistence for healthcare

Key facts: 100 million patients, 50 countries, one relational database, queries over 30 seconds, HIPAA, GDPR and PDPA.

### (a) Polyglot persistence (10 marks)

- **Definition**: use several database types, each for the data and access pattern it handles best.
- **Rigid schema**: genomic and wearable data change shape; every new field needs a migration.
- **Scaling**: an RDBMS scales mostly vertically; 100 million patients outgrow one server.
- **Slow joins**: images, time series and relationships forced into tables cause 30 second queries.

| Data | Store |
|---|---|
| Billing, prescriptions | Relational (ACID) |
| Patient profiles | Document (MongoDB) |
| Wearable time series | Column-family (Cassandra) |
| Recent vitals cache | Key-value (Redis) |
| Trials, referrals | Graph (Neo4j) |
| X-rays, MRIs | Object storage + metadata |

- **Costs**: more systems to run and secure; keep stores in sync with Kafka or change data capture.
- **Compliance in every store**: encryption, access control, audit logs, EU data kept in EU regions.

Remember: right store per data type, sync, compliance everywhere.

### (b) Four NoSQL types (10 marks)

| Type | Model | Example | Healthcare use | Weak at |
|---|---|---|---|---|
| Key-value | key to opaque value | Redis, DynamoDB | latest vitals, sessions | queries not on the key |
| Document | nested JSON | MongoDB | patient profiles, imaging metadata | joins, multi-document transactions |
| Column-family | rows by key, column families | Cassandra, HBase | monitoring streams, genomic variants | ad hoc queries |
| Graph | nodes and edges | Neo4j | clinical trials, drug interactions | bulk scans |

- **Profiles**: one read returns the whole record; new fields need no migration.
- **Imaging**: metadata in documents, files in object storage.

Remember: four models, one product each, one use each, one weakness each.

## Question 3 (20 marks): Fraud rings with Spark GraphX

Key facts: millions of claims, about 10 percent fraudulent, about 1 billion dollars lost a year; rules miss rings that share addresses, phones and providers.

### (a) GraphX concepts and the claims graph (10 marks)

- **Property graph**: directed multigraph with properties on vertices and edges.
- **VertexRDD**: `(VertexId, properties)` for people, claims, providers, addresses, phones.
- **EdgeRDD**: `Edge(src, dst, property)` such as FILED, LIVES_AT, REPAIRED_BY, USES.
- **Triplets**: an edge with both its vertices, e.g. "claimant X used shop Y".
- **Connected components** find large linked groups mixing many claimants with few addresses.
- **Triangle counting** finds tight clusters typical of staged accidents.
- **APIs**: GraphX is Scala and Java only; use GraphFrames from Python.

```
Person A --LIVES_AT--> Address 1 <--LIVES_AT-- Person B
   | FILED                                 | FILED
Claim 1 --REPAIRED_BY--> Shop X <--REPAIRED_BY-- Claim 2
```

- **Real time**: graph runs in batch every few hours; new claims are scored at once against its results.

Remember: vertices, edges, triplets, connected components.

### (b) PageRank (10 marks)

- **Measures importance**: a vertex scores high when many, or important, vertices link to it.
- **Formula**: PR(v) = (1 - d)/N + d x sum of PR(u)/outdeg(u) over vertices u linking to v, with d = 0.85.
- **Iterative**: every vertex starts equal and shares its score over its links until changes fall below a tolerance (10 to 20 rounds).
- **Pregel**: each round is a superstep; in GraphX `graph.pageRank(0.0001)`.
- **High scores** point to ring organisers, corrupt clinics or repair shops, and shared phones or bank accounts.
- **Use**: run per suspicious component, send top scores to investigators, and use as a model feature.
- **Guard**: a busy legitimate hospital also scores high; compare with its normal volume.

Remember: d = 0.85, convergence, organisers and providers, prioritise investigations.

## Question 4 (20 marks): Governance and data quality in healthcare

Key facts: 60 countries, 50 million patients, two breaches, over 75 million dollars in fines, 12 percent bad records, audits take 4 months.

### (a) Pillars of data governance (8 marks)

- **Ownership**: a governance council, a data owner per domain, stewards who fix issues.
- **Policies and standards**: HL7 FHIR, ICD-10, LOINC; retention rules per country.
- **Data quality**: checks at ingestion and a quality score per source.
- **Security and privacy**: encryption, pseudonymised ids, masking, role-based access.
- **Compliance**: HIPAA minimum necessary; GDPR consent, erasure, 72-hour breach reporting; data residency.
- **Metadata and lineage**: a catalog tracing every number back to its hospital.
- **Audit**: immutable access logs cut audits from 4 months to days.
- **Balance**: analysts use de-identified data by default; identifiable access is approved and logged.

Remember: ownership, privacy, compliance, lineage, audit.

### (b) Six data quality dimensions (12 marks)

| Dimension | Meaning | Healthcare check |
|---|---|---|
| Accuracy | matches reality | lab values within clinical ranges |
| Completeness | required data present | patient id, birth date, diagnosis not null |
| Consistency | same fact everywhere | birth date equal in EHR, lab and billing; standard units |
| Timeliness | available when needed | lab results within 1 hour, alerts in seconds |
| Validity | follows rules and formats | ICD-10 code exists; discharge after admission |
| Uniqueness | one record per patient | master patient index merges duplicates |

- **Validate at ingestion** and send bad records to a quarantine table with the reason.
- **Profile daily** and show a quality score per hospital.
- **Detect anomalies**: sudden drops in volume or jumps in values reveal faulty feeds.
- **Fix at the source** so the 12 percent error rate falls; tools: Great Expectations or Deequ.

Remember: six dimensions, a check for each, quarantine, master patient index.

## Question 5 (20 marks): Cloud cost optimisation

Key facts: clients on AWS, Google Cloud and Azure often spend 50 percent or more over budget.

### (a) Cost drivers (10 marks)

- **Storage**: priced per GB-month plus per request; copies, no deletion and small files add up.
- **Compute**: usually the biggest share; clusters sized for peak and left idle at night.
- **Inefficient queries**: `SELECT *` on unpartitioned tables and skewed jobs waste hours.
- **Streaming**: runs 24/7, so waste repeats every hour.
- **Data transfer**: egress and cross-region or cross-zone traffic is charged per GB.
- **Managed service premiums** for managed Kafka, Spark and warehouses.
- **No visibility**: without tags per team, nobody owns the bill.
- **Example**: a 20-node cluster at 1 dollar per node-hour running 24/7 costs about 14,400 dollars a month, even if busy 6 hours a day.

Remember: storage, compute, transfer, visibility.

### (b) Storage optimisation (10 marks)

| Tier | Access | Example | Data |
|---|---|---|---|
| Hot | daily | S3 Standard | last 30 days |
| Warm | monthly | S3 Standard-IA, GCS Nearline | 1 to 6 months |
| Cold | rarely | Glacier Instant, GCS Coldline | audit history |
| Archive | almost never | Glacier Deep Archive | legal retention |

- **Tiering trade-off**: colder tiers cost far less per GB but charge for and delay retrieval.
- **Compression**: CSV and JSON to Parquet or ORC with Snappy or ZSTD, often 5 to 10 times smaller and cheaper to scan.
- **Lifecycle rules**: move data by age automatically and delete staging data after 7 days.
- **Deduplication**: one curated copy shared by teams, incremental loads instead of full copies.
- **By data type**: compact small files into 128 MB to 1 GB files; video is already compressed, so tier it.
- **Example**: 500 TB of JSON becomes about 100 TB of Parquet; moving 80 percent to cold cuts about 11,500 dollars a month to about 1,000.

Remember: tiering, Parquet, lifecycle rules, deduplication.

## Question 6 (20 marks): Feature engineering with Spark MLlib

Key facts: rules miss about 15 percent of fraud, churn found too late, credit scoring takes over 48 hours, sub-second scoring wanted.

### (a) The MLlib feature pipeline (10 marks)

- **StringIndexer** (estimator): maps each category to a number, e.g. merchant category.
- **OneHotEncoder**: turns indexes into 0/1 vectors so categories are not treated as ordered.
- **VectorAssembler** (transformer): joins all columns into one `features` vector.
- **StandardScaler**: rescales features so amounts up to 1,000,000 do not drown counts up to 50.
- **Missing data**: `Imputer` with the median, plus a "missing" flag column.
- **New categories**: `handleInvalid="keep"` stops unseen values from crashing scoring.
- **Fit on training data only** to avoid leakage; the same pipeline then scores new data.

```python
indexer = StringIndexer(inputCols=cats, outputCols=[c + "_idx" for c in cats], handleInvalid="keep")
encoder = OneHotEncoder(inputCols=[c + "_idx" for c in cats], outputCols=[c + "_vec" for c in cats])
assembler = VectorAssembler(inputCols=nums + [c + "_vec" for c in cats], outputCol="raw")
scaler = StandardScaler(inputCol="raw", outputCol="features")
lr = LogisticRegression(labelCol="is_fraud", weightCol="class_weight")
model = Pipeline(stages=[imputer, indexer, encoder, assembler, scaler, lr]).fit(train_df)
```

Remember: estimator vs transformer, stage order, handleInvalid, no leakage.

### (b) Why feature engineering matters (10 marks)

- **Better features often beat a better algorithm**: a model only learns what its features show.
- **Velocity**: transactions in the last hour catch rapid fraud.
- **Ratio to normal**: amount divided by the customer's average flags unusual spending.
- **Location and device**: distance from usual place and new device flag catch account takeover.
- **Churn signals**: fewer logins and falling balances flag customers before they leave.
- **Imbalance**: use class weights; report precision, recall, F1 and PR-AUC, not accuracy.
- **Drift and leakage**: retrain daily; never use fields known only after fraud is confirmed.
- **Serving**: train in Spark daily, serve through a low-latency model server for sub-second scores.

Remember: derived features, imbalance metrics, drift, serving layer.
